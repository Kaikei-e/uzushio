# 0010: 審判の変更は三段階の実験票で見切る：時間枠、再利用キー、項目単位の再開、示唆はするが決めない

## ステータス

Accepted

採択日: 2026-09-06

## 日付

2026-09-06

## コンテキスト

### 評価の待ち時間が変更の数を決めている

0009 は審判の較正を決めた。較正は 200 項目 × 複数 seed × 6 コールで、所有者の経験報告では過去の
フル計測に **約 7 時間**かかっている（ジョブの内訳は特定できていない。`historical_breakdown: unknown`
として扱う）。この待ち時間が毎回の関門である限り、審判の設定を 1 つ変えて試すことに半日かかる。
試せない変更は試されないので、**評価の待ち時間そのものが品質改善の速度の上限**になっている。

所有者の要件は「速さは品質と同じだけ重要」であり、それは応答時間だけでなく
**変更を試して次の判断を得るまでの時間**にも当てはまる。

### 何が本当に必要か

判断は 2 種類ある。**少数で早く不採用にする判断**と、**一般化する品質改善の確認**である。
前者に較正の精度は要らない。後者に日常の頻度は要らない。両方を 1 つの手続きで
やろうとしていたことが、7 時間を毎回払っていた理由である。

### 保存資産

較正の 400 run（保存された `run.json` / `judge.json` / `select.json` / 候補本文）が既にある。
`cmoa judge --task … --candidate …` は外部候補を受けて判定だけを新しい run に残せるので、
提案者を再生成せずに審判だけを測り直せる。つまり **base 条件は多くの場合すでに測ってある**。
ただし保存 run を無条件に流用すると、別の prompt・別のビルド・別の judge 設定の結果を
同一条件として比較してしまう。

根拠は所有者の 2026-09-06 の内部調査メモ（統合レビュー版）の評価アジリティ節、および
Efficient Benchmarking（NAACL 2024）・tinyBenchmarks の subset 評価に関する報告である。
後二者は「小集合は判断への影響で検査する」という設計動機であって、本件の短縮率・精度の保証ではない。

## 決定

### D1. 三段階と時間枠

| 段階 | 入力 | 時間枠（新規投入停止の目標） | 出せる判断 |
|---|---|---|---|
| A: 動作と見込み | 開発側 4〜8 項目、固定 1 seed | **600 秒** | `drop` / `advance` / `inconclusive` |
| B: 開発比較 | 同じ開発 pool から追加、累計 最大 40 項目 | **1800 秒（A を含む累計）** | `drop` / `finalist` / `inconclusive` |
| C: 採用前確認 | 独立側、件数・条件・指標・合否を開始前に固定 | **5400 秒（別枠の初期見積り）** | `adopt` / `drop` / `inconclusive` |

**全 200 項目 × 2 seed の再実行を、各変更の必須条件にしない。** フル計測は最終候補 1 案に
絞ったあと、提案者を含むシステム変更、選択 protocol・対象分布の大きな変更、小規模結果と
過去の全件結果の判断逆転、のいずれかで必要性を検討する。

10/30/90 分は **CMoA の運用設計値**であり、論文由来の合格線でも達成済みの実測でもない。
時間枠を満たすために片順序へ落としたり、生成上限を黙って変えたりはしない。
同一 GPU で 2 条件を同時実行しない（runner は逐次に走らせる）。

### D2. 再利用キー

保存 run が base 条件の代わりになるのは、**キーが一致するときだけ**である。キーは
task.json のハッシュ、会話・ルーブリック・参照のハッシュ、候補本文のハッシュと**候補 ID 対応**、
`prompt_version`、`cmoa_version`、選択規則、judge 設定のダイジェスト（model / base_url /
temperature / max_tokens / output_format / parallel）、`allow_tie`、提示 seed、judge seed。

会話のハッシュは**ハーネス自身が run に書いた `conversation_sha256`** を使う。ハーネスは
ファイルのバイト列ではなく復号した会話の正準形をハッシュするので、こちらでファイルから計算すると
どの保存 run も間違った理由で不一致になる。比較するのは「保存 run に記録された値」と
「同じ項目についてこの trial が今作った run に記録された値」である。

`prompt_version` と `cmoa_version` と選択規則は**実際に作られた run からしか読めない**ので、
runner は候補条件の最初の 1 項目を走らせてから base の期待キーを解決する。judge 設定は
base の設定ファイルから直接ハッシュする。prompt を変える案では base の保存 run が全部
不一致になるが、それは安全な向きである——**そのときは base も測る**。

キーが違う結果を同一条件として扱わない。不一致になったフィールド名をレポートに出す。

### D3. 再開の単位は「項目 × 条件」

`Judge.Run` は途中コールの細粒度再開を保証しないので、初版の再開単位は項目とする。
runner は完了した (項目, 条件) を `results.jsonl` に 1 行ずつ追記し、`--resume` は
そこにある step を**二度と問い合わせない**。`--resume` 無しで既存 journal を上書きすることは
拒否する。既存 run は書き換えない。

設定変更・失敗隠し・都合のよい項目への差替えは再開と呼ばない。

### D4. 速度は同一セッションの両条件からしか出さない

速度差は同一負荷での **retry 込み平均 wall time** から `G_judge = 1 − mean(T_new)/mean(T_base)`。
**base を保存 run から再利用した回は、速度比を出さない。** 別の日・別の負荷の wall time を
今日の base として使わないという意味であり、レポートは比を空にして理由を書く。

判定だけを測り直したことを `G_judge` と明記し、`G_round` へ置き換えない。中央値は併記する。
**p95/p96 は A/B の合否に使わない**（この件数の裾は裾ではない）。

### D5. 品質の扱いは名前ごと数値に添える

扱いは `human-position-only, failure-as-zero`。人間が位置（c1/c2/c3）を指した項目だけを分母に入れ、
`no_candidate` は**定義された失敗として 0**、`judge_timeout` / `judge_failed` は機械の失敗として
どの成績にも入れず別に数える。人間ラベルが位置を指さない項目は評価不能として件数だけ残す。

3 候補すべての人間順位が無く、観測できるのがペア選好だけのときは **pair judge の評価**と名付け、
選択 top-1 の代わりとはしない。人間ラベルが無ければ「動作と速度は見た、品質は未確認」と書く。

### D6. 合否の目安は結果を見る前に実験票へ書く

| 案の目的 | B で finalist へ進める目安（点推定、保証ではない） |
|---|---|
| 速度を買う案 | ΔQ が **−2 pt 以上**、平均時間が **10% 以上短縮** |
| 品質を買う案 | ΔQ が **+3 pt 以上**、平均時間の増加が **5% 以内** |
| 出力不良の修正 | 狙った失敗例が直り、D で品質低下を認めない |

40 項目の単純平均では 1 件が 2.5 pt である。**B で −2 pt の非劣性を証明することは期待しない。**
閾値を用途別に変えるなら、結果を見る前に実験票で変える。

### D7. 停止語彙と、runner は決めない

停止理由は安定した英語の値と、メモの日本語語彙を並記する:
`completed`（完走）/ `malfunction`（動作不良）/ `early_cut`（早い見切り）/ `no_prospect`（見込みなし）/
`out_of_budget`（時間・資源切れ）/ `undetermined`（未確定）。
`completed` だけが本実装の追加であり、メモの 5 つは「早く止める規則」である。

時間切れによる中断は `inconclusive` であって、モデルの通常の invalid/timeout とは分ける。

runner が書くのは `suggested` だけで、**`decision` は人間が書く**。runner は `adopt` を出さない：
採用は母集団についての主張であり、A/B はそれを支えない。「新規に落とした正答が救済した誤答より
2 件以上多ければ落とす」は **開発用 heuristic** として明示的にそう名乗り、劣位の統計的証明とは書かない。
A/B のレポートに「確認済み」「有意」「非劣性」という語を付けない。

### D8. D / R / H の役割

初版は IRT や能動選択器を実装せず、**カテゴリ・入力長・言語を見た層別抽出**と、別枠の既知失敗例を使う。
D（開発代表、最大 40）の集計は目標母集団の層の比率で重み付けし、R（既知失敗、4〜8）は**別表示**する。
評価可能項目が 4 件に満たない層は **未評価**とし、平均を出さない。
H（調整に使っていない項目）は C 用に確保し、D/R で繰り返し調整した案の確認に使う。
R やハッシュ群を多く入れた集合の単純平均を全体精度として報告しない。

manifest は `{"schema_version":1,"set":"D"|"R"|"H","items":[{"id","strata","reason"}],"weights":{…}}`。
`weights` は任意（stage A の手作りセットには対応する母集団が無い）。重みのキーは層の**値**で、
1 項目が 2 つの重み付き層に属することは検証エラーにする。

### D9. 実験票を先に書き、レポートへそのまま埋める

事前に決めるのは仮説、変更 1 点、条件 ID と設定ファイルのハッシュ、再利用元、D/R/H の項目、
seed と judge seed、比較指標、合否・見切り、時間上限。runner はこれを**そのままレポートへ写す**。
結果を見てから動かした閾値は、票と結果が同じファイルにあるときだけ見える。

設定ファイルは実行前にハッシュを照合する。ローカル設定は実験の合間に編集されるものであり、
編集されたほうを黙って走らせた比較は「誰も書き留めていない 2 つ」の比較になる。

### D10. 初版の完成条件と、後回しにするもの

完成条件は **保存候補で judge を呼べる／時間枠で止められる／同じ完了項目を再実行しない／
未完了を隠さず比較レポートを返す** の 4 つ。CI 連携、高度な subset 選択、ダッシュボードの
全面整備は**その後**である。まず複数の実験票で 10 分の見切りと 30 分比較が実際に機能するかを測る。

## 根拠（調査結果・出典）

- 所有者の内部調査メモ（2026-09-06、統合レビュー版）の評価アジリティ節。7 時間は所有者の経験報告で、
  ジョブの内訳は未特定。
- Perlitz et al., *Efficient Benchmarking*, NAACL 2024 — 小集合は「判断への影響」で検査するという軸。
  CMoA の短縮率は保証しない。
- Polo et al., *tinyBenchmarks* — 少数例評価の可能性と分布変化への限界。単純な層別抽出を支持する参考で
  あって、8/40 項目の精度保証ではない。
- Howard et al., *Time-uniform confidence sequences*; *Stop Guessing When to Stop Testing* §5 —
  途中で止めて採用する運用に必要な統計基盤。**初版では実装しない**（D7 の理由）。
- 実装：`internal/judge/trial.go`、`internal/judge/trialreport.go`、`cmd/uzushio/trial.go`。
- 既存機能：CMoA の `cmoa judge --task … --candidate … --config …`（外部候補で判定だけを実行、
  `--seed` は提示側・`--judge-seed` は sampling 側）。時間枠・subset・再開・実験票は uzushio 側の追加。

## 検討した代替案

- **各変更でフル 200 項目 × 2 seed を再推論する（現状）**。不採用。1 変更 7 時間は、試せる案の数を
  決めてしまう。集計だけの変更は保存 400 run の replay で足りる（0009 の `--replay` / `--rescore-from`）。
- **保存 run を条件が近ければ流用する**。不採用。近さの判定を人間の記憶に任せると、prompt が
  変わった日の比較が静かに壊れる。キーの完全一致だけを流用の条件にする。
- **再利用した base の wall time を速度比に使う**。不採用。無料なのは、別の日の測定だからである。
- **高度な逐次統計・IRT・能動抽出を先に実装する**。後回し。初版は固定小集合・開発上の見切り・
  C の固定 n 判定で始められる。統計手法の実装が終わるまで A/B を止めることはしない。
- **runner が `adopt` まで出す**。不採用。固定 n の CI を項目ごとに見て初めて合格したところで
  止める運用と区別がつかなくなる。
- **コール単位で再開する**。見送り。`Judge.Run` が細粒度再開を保証しない。項目単位から始める。
- **`judge calibrate` にフラグを足す**。不採用。較正は「人間とどれだけ一致するか」を vault 文書に
  残す道具で、trial は「この変更に較正を払う価値があるか」を返す道具である。同じ名前で 2 つの仕事にしない。

## 影響とトレードオフ

- 得るもの：1 変更あたりの判断が分単位になる。base が再利用できる限り新規推論は候補条件だけ。
  実験票が結果と同じファイルに残るので、閾値の後付け変更が見える。
- 失うもの：4〜40 項目の点推定に統計的保証は無い。良い案を「早い見切り」で落とす可能性があり、
  runner はそれを記録するが防げない。速度比は base も測った回にしか出ない（その回は費用が倍になる）。
- リスク：小集合が full と判断を逆転させること。対策は逆転例を次版の R に加えることで、
  将来の H を消費しない。再利用キーは task.json とルーブリックを**現在の corpus** から読むため、
  「保存 run がそのルーブリックを見た」ことまでは保証しない（会話のダイジェストだけは保存 run 側と照合する）。
  この不一致は 2026-09-06 の最初の実機実行で見つかった：会話をファイルから計算していた版は、
  すべての保存 run を `conversation` の不一致として拒否していた。
